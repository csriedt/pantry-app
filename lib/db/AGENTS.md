# Database patterns

Everything that touches Postgres in this app — table definitions, migrations,
generated types — follows the conventions below. The canonical, well-formed
references to read while creating a table are:

- `lib/db/schema/catalog.ts` — the **global-or-owned** shape (catalog tables
  read by all users, writes scoped to the owner).
- `lib/db/schema/pantry.ts` — the **user-owned** shape, plus the doorbell
  (`pantry_state`).

Match their shape exactly: the same conventions, the same names, the same
order of concerns. Table *definitions* come from `pimp-my-pantry/SCHEMA.dbml`
— columns, the per-table note, and the access matrix / RTBF map at the top of
that file. The DBML decides shape; this file decides mechanics. When they
disagree, fix one of them deliberately — never let it ride.

_Last verified: 2026-10-14 against migrations `0000`–`0015` (schema, the RPC
pair + realtime publication, the write intents, the snapshot list section,
and the trusted-callable read twins); 242 tests green._

## What lives here

```
lib/db/
├── AGENTS.md               # this stamp
├── schema/
│   ├── index.ts            # barrel — drizzle-kit reads this as the schema entry
│   ├── catalog.ts          # canonical instance: global-or-owned tables
│   └── pantry.ts           # canonical instance: user-owned tables + doorbell
├── database.types.ts       # GENERATED by `npm run db:gen-types` — never hand-edit
drizzle/                    # migrations + meta snapshots (LF-pinned)
drizzle.config.ts           # kit wiring; loads .env.local natively
scripts/gen-types.mjs       # supabase CLI → database.types.ts
tests/rls.test.ts           # RLS boundary harness + access matrix
```

`database.types.ts` and everything under `drizzle/` are generated artifacts.
Human review happens at exactly one point: the generated migration SQL, before
it is applied.

## Rules

### Schema conventions

- **PK:** `uuid("id").primaryKey().defaultRandom()` — unless the DBML keys the
  table differently (`pantry_state` keys on `user_id`; no surrogate column).
- **Names:** TS properties camelCase, DB columns snake_case — always pass the
  column name explicitly: `ownerId: uuid("owner_id")`.
- **Enums:** `varchar(col, { length, enum: [...] })` **plus** a
  `check("<table>_<col>_valid", …)` constraint — belt and braces. Never
  `pgEnum`: altering a Postgres enum later is painful, and the TS union comes
  from the `enum` array anyway.
- **Timestamps:** `timestamp(col, { withTimezone: true })`. `created_at` →
  `.notNull().defaultNow()`. `updated_at` → app-set and nullable, *unless* the
  DBML gives it a default (the doorbell's does).
- **Tombstones:** `deleted_at` is NULL until the RTBF purge job (service role)
  sets it. A `defaultNow()` there stamps every new row as deleted — silent and
  fatal. Tombstones never get a default.
- **Unique with a nullable column:** add `.nullsNotDistinct()` (PG15+) or the
  constraint won't constrain rows where that column is NULL.
- **FKs:** user-owned rows reference `authUsers.id` from `drizzle-orm/supabase`
  with `{ onDelete: "cascade" }` — owned data is purged with the account.
  Catalog references cascade when the row is meaningless without them;
  otherwise leave the default. Self-references need the `AnyPgColumn`
  annotation: `parentId: uuid("parent_id").references((): AnyPgColumn =>
  categories.id)`.
- **Numerics:** explicit `precision`/`scale`. Never float, never bare numeric.
- **Name every constraint and policy explicitly** (`unique`, `check`,
  `pgPolicy`); FKs may carry drizzle's generated names.
- **One layer file per DBML group**, exported from the barrel: catalog,
  pantry, recipes, meals, trends, ai, lifecycle.

### Policies

- Use `to: authenticatedRole` and the wrapped claim reader `${authUid}` — both
  from `drizzle-orm/supabase`. **Never a bare `auth.uid()`**: the wrapper
  (`(select auth.uid())`) makes Postgres evaluate it once per statement, not
  once per row.
- Own-row predicate: `` sql`${table.userId} = ${authUid}` ``. The **same**
  predicate in `using` and `withCheck` — `using` guards what you can see,
  `withCheck` guards what you can write; an insert/update policy without it
  writes other users' rows.
- `delete` policies carry `using` only — there is no new row to check.
- Read-only catalog tables get a select policy with `` using: sql`true` `` and
  **no write policies at all**.
- Server-only tables (the ai group) get `.enableRLS()` and no policies — deny
  by default.

### Grants — the trap

**drizzle-kit emits policies but never grants.** Policies without grants mean
`42501 permission denied` at runtime, and nothing in the generated SQL warns
you. Every table gets a hand-appended grant block, with the ops read off its
access-matrix line in the DBML:

```sql
GRANT <ops from the matrix> ON TABLE "<table>" TO "authenticated";--> statement-breakpoint
GRANT ALL ON TABLE "<table>" TO "service_role";--> statement-breakpoint
```

`service_role` needs grants regardless of RLS — it bypasses RLS, not
privileges. The ops are per table, not per group: `pantry` carries DELETE (the
sheet's Remove), `shopping_list_items` carries delete but not update (checkoff
deletes; nothing edits), `pantry_state` carries write ops because the future
invoker RPC bumps it.

### Functions (RPCs)

- **Drizzle does not create functions.** There is no `.ts`-first step: the
  migration's hand-written SQL is the source of truth and
  `database.types.ts` regenerates *after*, from the live DB — the opposite
  direction from tables. `npx drizzle-kit generate --custom --name=<slug>`
  yields an empty `.sql` plus its journal entry and snapshot; you hand-write
  the SQL into it.
- **Dry-run hand-written SQL before migrating.** Rehearse the file in
  `BEGIN … ROLLBACK` against the dev DB — a typo in a function body is much
  cheaper to catch before the ledger advances. (`0004`'s silent-XOR body was
  caught by a test, which is why `0006` exists.)
- **`SECURITY INVOKER` always.** The function runs as the caller, so RLS
  gates it; `auth.uid()` resolves from the client's JWT and there is no user
  argument. `SET search_path = ''` with every reference schema-qualified, and
  the claim reader wrapped — `(select auth.uid())`.
- **Write intents own the doorbell.** The function body is the transaction:
  the row writes and the `pantry_state` bump create-or-increment in the same
  call (`values (uid, 1, 'user', now())` on conflict do update
  `state_version = state_version + 1`), and the new version is returned so the
  client advances its cached copy without a re-read. Read intents return
  `{version, items}` from ONE statement — version and rows share a snapshot.
- **Arguments land as given.** Never silently reinterpret (dropping an amount
  because a stock_state also arrived, say) — the table's checks are the guard
  and raise by constraint name.
- **`EXECUTE` needs granting too.** `GRANT EXECUTE ON FUNCTION <sig> TO
  "authenticated";` plus `ALL` for `service_role`, and
  `REVOKE EXECUTE … FROM PUBLIC` — Postgres grants functions to PUBLIC by
  default, which contradicts the fails-closed posture.
- **Write intents return the new version** so the client advances its
  cached copy without a re-read. The one exception: an intent whose row a
  later intent must address returns the identity too —
  `commit_meal` returns `{ meal_id, version }` (the receipt undoes by id,
  and a select-after-insert would be a two-device race).
- **`CREATE OR REPLACE` cannot change a return type.** A signature change
  (return type, parameter list) needs `DROP FUNCTION` first — and the drop
  takes the grants with it, so the migration re-applies them (`0013`).
- **Definer is the exception, and it must own its check.** Only for writes
  the user matrix denies an UPDATE/INSERT grant for (today:
  `cancel_deletion_request` — the 0002 pass chose a definer RPC over
  widening `deletion_requests` grants). Definer bypasses RLS, so the
  internal `user_id = auth.uid()` filter IS the policy; a definer function
  without one is a hole. No doorbell bump unless the function moves pantry
  state.
- **Calling a jsonb-taking RPC through postgres.js (tests, scripts): pass
  the raw JS value under a `::jsonb` cast.** postgres.js serialises the
  value from the cast context, so an array lands as a jsonb array; a
  pre-`JSON.stringify`-ed string lands as a jsonb *scalar* and every
  `jsonb_array_elements` on it dies with "cannot extract elements from a
  scalar". Supabase-js (JSON bodies) is unaffected.
- **Never edit an applied function.** Replace with a new
  `CREATE OR REPLACE FUNCTION` migration; the old version stays in history
  (`0004` → `0006`).
- **User-scoped reads come in pairs** when a trusted caller needs them:
  `get_x()` (identity from `auth.uid()`, token-scoped) and
  `get_x_for(p_user_id)` (identity from the argument, for the cached read
  — ADR 0001). The twin repeats the `where user_id = p_user_id` filter
  rather than delegating through a claim-forging wrapper, and stays
  SECURITY INVOKER so RLS backstops token calls. A twin returns
  `SETOF <table>` when the rows are already the wire shape
  (`list_meals_for`) and jsonb only when the read composes an envelope
  (`get_pantry_snapshot_for`) — whichever keeps the mapper's job to
  narrowing rather than parsing.

### Realtime

- **Publish signaller rows only.** The `supabase_realtime` publication
  carries `pantry_state` and `recipe_trend_runs` (`0005`) — the domain
  doorbells — and nothing else. The rule is about **width, not
  frequency**: a signaller row may be bumped by every write in its domain,
  because a row update is thin data and the client's refetch is the only
  cost. Ringing the bell liberally is not a reason to widen the
  publication, and narrowing it is not a reason to go quiet.
- **Realtime is JWT-gated by RLS** — a subscriber only receives changes to
  rows it can SELECT, so each channel is scoped by the policy (own-row
  for `pantry_state`, read-all for `recipe_trend_runs`), never by the
  client's own filter.

### Migration workflow

- **Never `push`.** `db:generate` / `db:migrate` only — push drops RLS SQL.
- **Review the generated SQL before applying.** Expected shape: `CREATE
  TABLE`, `ENABLE ROW LEVEL SECURITY`, constraints, FKs (auth.users with
  cascade), policies with `(select auth.uid())`. You should never see
  `CREATE SCHEMA "auth"` — if you ever do, stop and re-derive.
- **One statement per chunk.** `--> statement-breakpoint` is the migrator's
  chunk delimiter — functional, not a comment. Hand-appended statements need
  the marker **at the junction**: the generated file does not end with one.
- Append the grants at the end, then migrate, then (re)generate types.
- **Never hand-edit an applied migration.** If the group isn't live yet (check
  `information_schema.tables`), squash instead: delete the `.sql` and its
  snapshot, drop the entry from `meta/_journal.json`, regenerate once.
- `_journal.json` ordering decides what runs: an entry whose `when` is below
  the dev DB's ledger high-water mark
  (`select created_at from drizzle.__drizzle_migrations order by created_at
  desc limit 1`) is skipped forever, silently.
- **Migration + snapshot + regenerated types commit together.**

### Types

- `lib/db/database.types.ts` is generated by `npm run db:gen-types` after every
  migrate. Never hand-edit it. Drift check, when CI exists: regenerate, then
  `git diff --exit-code`.

## Stamping a new table (or group)

1. **Read the DBML entry** — columns, the note, and the access-matrix + RTBF
   lines at the top of `pimp-my-pantry/SCHEMA.dbml`. They decide columns,
   policies, grants, and FK actions.
2. **Pick the layer file and canonical instance** — extend the group's file in
   `lib/db/schema/`; copy the ownership shape from `catalog.ts`
   (global-or-owned) or `pantry.ts` (user-owned / doorbell).
3. **Write the table** per the conventions above; export it from the barrel
   `lib/db/schema/index.ts`.
4. **`npm run db:generate`**, then review the SQL against the rules above.
5. **Append the grants** (breakpoint at the junction) read off the matrix.
6. **`npm run db:migrate` → `npm run db:gen-types`.**
7. **Extend `tests/rls.test.ts`** with the matrix cases: own rows
   readable/writable, another user's rows invisible, catalog globals readable,
   boundary-crossing writes rejected, server-only unreachable (when the ai
   group lands). Use randomized seeds so the suite never collides with real
   data, and the `attempt` / `failureOf` savepoint helpers for expected
   failures.
8. **`npm run lint` + `npx tsc --noEmit` + `npm test`** — then commit migration
   + snapshot + types together.

The DB suite skips when `DATABASE_URL` is unset, so `npm test` stays green
without a database; when it is set, the suite doubles as the free-tier
project's keepalive (projects pause after roughly seven idle days).

## Stamping a function (RPC)

1. **Confirm the contract** — the DBML entry and `DESIGN.md` §8 decide the
   shape: invoker, one-statement reads, the doorbell rule, the name
   (`upsert_<entity>` / `commit_<entity>`), and the return (the envelope, or
   the new version).
2. **`npx drizzle-kit generate --custom --name=<slug>`**, then hand-write the
   SQL per the rules above — read + write halves, the doorbell bump, grants.
3. **Dry-run in `BEGIN … ROLLBACK`** against the dev DB before applying.
4. **`npm run db:migrate` → `npm run db:gen-types`** — the `Functions` block
   in `database.types.ts` is the generated side of the RPC.
5. **Extend `tests/rls.test.ts`** (the RPC pair suite): call the functions as
   forged users — invoker enforcement, one-snapshot agreement, doorbell
   create-or-increment with an exact +1, cross-user isolation, arguments
   landing as given. `failureOf` for expected rejections.
6. **`npm run lint` + `npx tsc --noEmit` + `npm test`** — then commit with the
   migration + snapshot + regenerated types (function migrations carry no
   schema diff, but the journal entry still advances).
